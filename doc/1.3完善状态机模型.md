# 1.3 完善状态机模型

本阶段依据 `doc/RMS_Agent说明.md`、`doc/1.1业务对象.md` 以及上一阶段 `ScenarioModel`，建立通用、可校验、可复用的任务状态机数据模型，用于描述仓储任务从创建、等待、调度、执行到完成、失败、取消或超时的完整状态流转。

本阶段只实现状态机的数据结构、枚举、引用校验、图结构校验、示例和测试，不实现状态机运行引擎、任务调度算法、规则执行器、guard 表达式解析器、action 实际执行逻辑、数据库、API、Web 页面或可视化编辑器。

## 模型清单

代码位于 `src/irms/models/state_machine/`：

- `State`：任务状态
- `Transition`：状态流转
- `StateMachine`：状态机组合模型
- `Action`：动作描述，仅结构化保存，不执行
- `Guard`：守卫条件描述，仅结构化保存，不解析、不执行
- `StateType`：状态类型枚举
- `TransitionType`：流转场景类型枚举
- `TriggerType`：触发类型枚举

`StateMachine` 使用 `task_type_id`、`task_flow_id` 与上一阶段 `TaskType`、`TaskFlow` 建立 ID 引用，避免模型之间循环嵌套。

## 超时字段

- `State.timeout`：进入该状态后允许停留的最大时长。
- `Transition.timeout`：触发流转前的等待或判定时限。
- 时间单位统一为秒。
- 未明确的超时时间保留为 `null`，不自行填写业务默认值。

## 校验规则

`StateMachine` 会进行以下确定性校验：

- 状态 ID 不可重复。
- 流转 ID 不可重复。
- `from_state` 必须引用存在的状态。
- `to_state` 必须引用存在的状态。
- `initial_state_id` 必须引用真实存在的状态。
- 状态列表中必须且只能存在一个 `INITIAL` 类型状态。
- `initial_state_id` 指向的状态必须是唯一 `INITIAL` 状态。
- 至少存在一个终止状态。
- `COMPLETED`、`FAILED`、`CANCELLED` 必须设置 `terminal=true`。
- `terminal=true` 仅允许用于 `COMPLETED`、`FAILED`、`CANCELLED`。
- 终止状态不能存在普通向外流转；如确需恢复，必须显式使用 `transition_type=RECOVERY` 且 `allow_from_terminal=true`。
- 禁止状态流转到自身，除非 `allow_self_loop=true`。
- 流转优先级必须为非负整数。
- 状态超时和流转超时必须大于 0。
- 同一来源状态下，相同触发器、相同优先级、相同 guard 的流转不得指向不同目标状态。
- 所有非初始状态至少存在一条入边。
- 所有非终止状态至少存在一条出边。
- 从初始状态出发，所有状态应可达。
- 检测完全孤立的状态。
- 检测没有路径到达任何终止状态的分支。

## 示例

完整 JSON 示例：

- `examples/basic_task_state_machine.json`

主路径：

```text
INITIAL
→ WAITING
→ DISPATCHING
→ EXECUTING
→ COMPLETED
```

分支：

```text
EXECUTING → FAILED
WAITING → CANCELLED
EXECUTING → BLOCKED
BLOCKED → EXECUTING
BLOCKED → FAILED
```

## 测试

基础测试位于 `tests/test_state_machine.py`，覆盖：

- 合法状态机
- 多个初始状态
- 初始状态不存在
- 重复状态 ID
- 重复流转 ID
- 流转引用不存在的状态
- 不存在终止状态
- 不可达状态
- 终止状态存在非法向外流转
- 超时时间非法
- 流转冲突

## 当前仍需人工确认的问题

- 各任务状态的正式名称、状态码和合法流转关系。
- 哪些任务失败、取消或人工处理状态属于正式终态。
- 自动重试次数、重试间隔、阻塞超时、调度超时等具体阈值。
- guard 表达式语言、变量命名和是否允许复合条件。
- action 编码、参数格式和动作执行边界。
- 挂起、恢复、终止状态恢复是否需要更严格的审批机制。
- 不同任务类型是否需要扩展更细的内部步骤状态。
